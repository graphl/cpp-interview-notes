# C++ 面试题：Linux 调试工具如何选择

## 1. 先按证据类型选择工具

```text
程序已经崩溃？
  -> core dump + gdb + addr2line/反汇编

程序还活着但行为错误？
  -> 日志、gdb attach、strace、系统状态

怀疑内存生命周期错误？
  -> ASan；无法重编译时考虑 Valgrind

怀疑数据竞争？
  -> TSan + 并发事件/锁证据

怀疑 CPU 热点？
  -> perf record/report + 火焰图

怀疑睡眠、锁或 IO 等待？
  -> off-CPU 分析、futex/调度 trace、strace

需要观察内核调用链和事件时间线？
  -> ftrace/trace-cmd/perf/bpftrace
```

## 2. 工具和证据映射

| 工具 | 最擅长回答 | 不能单独证明 |
|---|---|---|
| GDB | 当前线程状态、断点、寄存器、内存、调用栈 | 长时间系统级性能趋势 |
| core dump | 崩溃瞬间的线程和内存快照 | 崩溃前完整时间线 |
| strace | 系统调用、返回值、阻塞位置 | 用户态函数内部热点 |
| ltrace | 动态库函数调用（受平台/优化影响） | 内联代码和完整系统行为 |
| ASan/UBSan | 被执行路径上的内存错误/部分 UB | 未覆盖路径、所有并发协议错误 |
| TSan | 动态执行中的数据竞争 | 所有死锁、业务原子性问题 |
| Valgrind | 无需重新插桩编译的内存检查（平台相关） | 低开销生产观测 |
| perf | 采样热点、硬件计数器、调度事件 | 单次业务请求的完整因果链 |
| ftrace/trace-cmd | 内核函数和 tracepoint 时间线 | 任意用户态高级语义 |
| bpftrace | 动态聚合内核/用户探针 | 无验证的脚本结论和所有平台兼容性 |
| readelf/objdump | ELF 元数据、符号、重定位、机器指令 | 运行时状态本身 |

## 3. 标准调查闭环

```text
记录症状和时间窗口
  -> 保存版本、配置、日志和系统指标
  -> 判断进程是否崩溃/卡住/变慢/结果错误
  -> 选择最小侵入工具取得第一份证据
  -> 缩小到线程、系统调用、函数或对象
  -> 提出可证伪假设
  -> 用第二种独立证据或最小实验验证
  -> 修复后复现原负载并检查回归
```

## 4. 三个典型组合

### 崩溃

```text
coredumpctl/gdb
  -> thread apply all bt full
  -> 寄存器与反汇编
  -> 匹配源码和对象生命周期
  -> ASan 复现内存破坏来源
```

### 卡住

```text
ps/top 判断线程状态
  -> gdb 所有线程栈
  -> strace 判断系统调用阻塞
  -> perf sched/ftrace 检查锁与调度
```

### 变慢

```text
业务延迟与系统指标
  -> USE 方法确定资源
  -> perf 找 on-CPU 热点
  -> off-CPU/锁/IO trace 找等待
  -> 对照实验验证
```

## 5. 线上使用边界

1. `gdb attach`、详细 strace 和高频探针可能暂停或显著影响进程。
2. perf/bpf/ftrace 的权限、内核配置和采样频率需要提前确认。
3. 调试输出可能包含请求内容、地址和密钥等敏感信息。
4. 先保存现场再重启；但高风险故障仍应优先止损并遵守变更流程。
5. 所有结论记录构建版本、时间戳、命令和采样参数，保证可复核。

## 6. 面试口述版

我会先按问题类型选择证据：崩溃看 core 和 GDB，系统调用阻塞看 strace，内存错误看 ASan，数据竞争看 TSan，CPU 热点看 perf，内核时间线看 ftrace 或 bpftrace。任何工具输出都只是证据，最终要形成症状、范围、假设、独立验证和修复复测的闭环。
