# C++ 面试题：ASan、UBSan 和 TSan 怎么选

## 1. 三类工具解决的问题不同

| 工具 | 主要发现 | 典型问题 |
|---|---|---|
| ASan | 非法内存访问和部分生命周期错误 | 越界、use-after-free、double free |
| UBSan | 部分未定义行为 | 有符号溢出、错误对齐、非法转换 |
| TSan | 线程间数据竞争 | 无同步的共享变量读写 |

Sanitizer 通过编译器插桩，在关键内存访问或运算周围加入运行时检查；它不是单纯读取 core 文件的离线工具。

## 2. 数据流

```text
源代码
  -> 编译器插入检查逻辑
  -> 链接 sanitizer runtime
  -> 运行测试/服务
  -> runtime 维护影子状态
  -> 检测到违规访问或竞争
  -> 输出访问地址、线程、分配释放栈和源码位置
```

## 3. 常用构建方式

```bash
# 内存错误 + 常见未定义行为
clang++ -g -O1 -fno-omit-frame-pointer \
  -fsanitize=address,undefined app.cpp -o app_asan

# 数据竞争，单独构建
clang++ -g -O1 -fno-omit-frame-pointer \
  -fsanitize=thread app.cpp -o app_tsan
```

ASan 与 TSan 通常不能在同一个二进制中组合，应建立不同测试构建。GCC 和 Clang 的具体可用选项、平台支持和 runtime 行为需要结合工具链版本验证。

## 4. 如何读一份 ASan 报告

```text
错误类型：heap-use-after-free
  -> 当前非法访问栈
  -> 目标地址所属内存块
  -> 该内存块的释放栈
  -> 原始分配栈
```

不要只修崩溃行。应回答：谁仍持有悬空引用、所有权协议为什么允许对象先释放、怎样让类型或 RAII 结构阻止同类错误。

## 5. TSan 报告表达什么

TSan 通常给出两个可能并发且没有建立 happens-before 的冲突访问，以及相关线程创建栈。报告指出数据竞争证据，但业务层修复仍需确定共享状态的不变量，选择锁、原子变量、线程封闭或消息传递。

## 6. 局限性

1. 插桩会增加内存和运行时间开销，不宜未经评估直接替代普通生产构建。
2. 只有被测试路径实际执行，相关问题才可能被发现。
3. 自定义汇编、未插桩库和特殊内存管理可能降低可见性。
4. TSan 发现的是数据竞争，不保证发现所有死锁和高级并发协议错误。
5. sanitizer 报告也要保留构建版本、符号和复现输入。

## 7. 面试口述版

ASan 主要查越界和 use-after-free，UBSan 查部分未定义行为，TSan 查没有 happens-before 的数据竞争。它们依赖编译器插桩和运行时影子状态，因此适合测试和复现环境。ASan/UBSan 与 TSan 通常分开构建；报告要沿非法访问、分配释放栈或冲突线程继续追踪所有权和同步协议，而不是只改报错行。
