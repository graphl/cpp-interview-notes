# 07 内存碎片或分配器缓存

## 1. 类型定义

内存碎片或分配器缓存不是严格意义上的内存泄漏。

程序可能已经释放了内存，但内存分配器没有立刻把内存归还给操作系统，或者由于频繁申请释放不同大小对象，导致可用内存碎片化。

---

## 2. 典型现象

```text
业务对象已经释放
Valgrind 不报明显泄漏
RSS 仍然不下降
heap 曾经增长，释放后没有回落
高并发、大量小对象分配场景常见
```

---

## 3. 原因示例

```text
glibc malloc arena 缓存
频繁分配释放不同大小内存块
多线程导致多个 arena
对象大小不稳定
内存池只扩不缩
```

示例：

```cpp
std::vector<std::string> data;

void load() {
    for (int i = 0; i < 1000000; ++i) {
        data.push_back(std::string(100, 'x'));
    }
    data.clear(); // size 清零，但 capacity 可能不释放
}
```

---

## 4. 排查方法

看是否真的还有对象存活：

```bash
valgrind --leak-check=full ./app
heaptrack ./app
```

看进程内存：

```bash
cat /proc/<pid>/smaps
pmap -x <pid>
```

如果使用 jemalloc：

```bash
MALLOC_CONF=stats_print:true ./app
```

glibc 可观察：

```cpp
malloc_info(0, stdout);
```

---

## 5. 修复或优化方式

释放 vector 容量：

```cpp
std::vector<int>().swap(v);
```

或：

```cpp
v.clear();
v.shrink_to_fit();
```

减少频繁小对象分配：

```text
对象池
内存池
复用 buffer
预分配容量 reserve
统一对象大小
```

调整分配器：

```text
jemalloc
tcmalloc
自定义 allocator
```

---

## 6. 面试总结

RSS 不下降不一定是泄漏，也可能是内存碎片或分配器缓存。排查时要结合 Valgrind、heaptrack 和 smaps 判断对象是否还存活，再考虑容器 capacity、malloc arena 和内存池策略。
