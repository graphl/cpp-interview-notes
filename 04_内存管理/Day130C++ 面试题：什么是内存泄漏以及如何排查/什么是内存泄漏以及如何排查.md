## 1. 面试题

在一个长期运行的 C++ 服务中，发现进程内存持续上涨，最终可能触发 OOM。请说明：

1. 什么是内存泄漏？
2. 如何判断程序是否真的发生了内存泄漏？
3. 你会使用哪些工具进行排查？
4. 常见的代码原因有哪些？
5. 实际开发中如何避免内存泄漏？

## 2. 核心结论

内存泄漏是指程序申请了内存，但是在不再使用之后没有释放，导致这部分内存一直被占用。

在 C++ 中，内存泄漏通常发生在堆内存或资源生命周期管理不清晰的地方。长期运行的服务如果持续泄漏，可能导致：

1. 进程 RSS 持续上涨
2. 系统可用内存减少
3. 性能下降
4. 触发 OOM
5. 服务崩溃或被系统杀死

一句话回答：

> C++ 内存泄漏的本质是资源所有权没有被正确释放，排查时要先确认内存增长现象，再用工具定位分配栈，最后从 RAII、智能指针、异常路径和容器生命周期等方向修复。

## 3. 常见原因

### 3.1 new/delete 不匹配

```cpp
void func() {
    int* p = new int(10);
    // 忘记 delete p
}
```

修复：

```cpp
void func() {
    auto p = std::make_unique<int>(10);
}
```

---

### 3.2 new[]/delete 使用错误

```cpp
void func() {
    int* arr = new int[100];
    delete arr; // 错误，应该使用 delete[]
}
```

修复：

```cpp
void func() {
    int* arr = new int[100];
    delete[] arr;
}
```

更推荐：

```cpp
void func() {
    std::vector<int> arr(100);
}
```

---

### 3.3 malloc/free 不匹配

```cpp
void func() {
    char* buf = static_cast<char*>(malloc(1024));
    // 忘记 free(buf)
}
```

修复：

```cpp
void func() {
    std::vector<char> buf(1024);
}
```

---

### 3.4 异常路径或提前 return 导致释放逻辑没走

```cpp
void func(bool error) {
    char* buf = new char[1024];

    if (error) {
        return; // 泄漏
    }

    delete[] buf;
}
```

修复：

```cpp
void func(bool error) {
    auto buf = std::make_unique<char[]>(1024);

    if (error) {
        return;
    }
}
```

---

### 3.5 shared_ptr 循环引用

```cpp
#include <memory>

struct B;

struct A {
    std::shared_ptr<B> b;
};

struct B {
    std::shared_ptr<A> a;
};

void func() {
    auto a = std::make_shared<A>();
    auto b = std::make_shared<B>();

    a->b = b;
    b->a = a; // 循环引用，引用计数无法归零
}
```

修复：

```cpp
struct B;

struct A {
    std::shared_ptr<B> b;
};

struct B {
    std::weak_ptr<A> a;
};
```

---

### 3.6 容器只增不删

```cpp
std::vector<int*> cache;

void add() {
    cache.push_back(new int(10));
}
```

如果没有释放或清理策略，长期运行会持续增长。

修复：

```cpp
std::vector<std::unique_ptr<int>> cache;

void add() {
    cache.push_back(std::make_unique<int>(10));
}
```

如果是业务缓存，还要设计淘汰策略，例如 LRU、容量上限、过期时间。

## 4. 排查步骤

### 4.1 先确认内存增长现象

常用命令：

```bash
top
htop
ps aux | grep app
cat /proc/<pid>/status
cat /proc/<pid>/smaps
pmap -x <pid>
```

重点观察：

```text
VmRSS
VmSize
RssAnon
heap
```

如果进程内存持续上涨，需要进一步判断是：

1. 真正的内存泄漏
2. 正常缓存增长
3. 内存碎片
4. 线程栈增长
5. mmap 映射增长
6. 文件句柄、socket、GPU buffer 等资源泄漏

---

### 4.2 使用 Valgrind 定位

```bash
valgrind --leak-check=full --show-leak-kinds=all ./app
```

常见输出类型：

```text
definitely lost
indirectly lost
possibly lost
still reachable
```

重点关注：

```text
definitely lost
indirectly lost
```

它们通常表示真实泄漏。

---

### 4.3 使用 AddressSanitizer

编译：

```bash
g++ -fsanitize=address -g main.cpp -o app
```

运行：

```bash
./app
```

ASan 可以帮助发现：

1. memory leak
2. use after free
3. double free
4. heap buffer overflow
5. stack buffer overflow

如果需要检测泄漏，可配合：

```bash
ASAN_OPTIONS=detect_leaks=1 ./app
```

---

### 4.4 使用 heaptrack

适合排查长期运行进程的堆内存增长：

```bash
heaptrack ./app
heaptrack_gui heaptrack.app.gz
```

它可以看到：

1. 哪些调用栈分配最多
2. 哪些对象长期未释放
3. 内存峰值在哪里
4. 分配热点函数在哪里

---

### 4.5 使用 gperftools

适合线上或压测环境下分析堆分配：

```bash
HEAPPROFILE=./heap ./app
```

然后使用 pprof 分析内存增长来源。


## 6. 面试回答模板

如果面试官问：“C++ 内存泄漏如何排查？”

可以这样回答：

> 我会先确认内存增长是否稳定复现，例如通过 top、ps、/proc/pid/status、smaps、pmap 等观察 RSS、heap、mmap 的变化。确认确实存在异常增长后，再区分它是内存泄漏、缓存增长还是内存碎片。  
>  
> 工具上，离线场景我会优先使用 Valgrind，它可以给出未释放内存的申请栈；开发和测试阶段我会开启 AddressSanitizer，检查 leak、use after free、double free、越界访问等问题；如果是长期运行服务，可以使用 heaptrack 或 gperftools 分析堆分配热点。  
>  
> 代码层面我会重点检查 new/delete、malloc/free 是否匹配，异常路径或提前 return 是否导致释放逻辑没执行，容器中保存的裸指针是否释放，shared_ptr 是否存在循环引用，以及全局缓存是否缺少淘汰策略。  
>  
> 修复上，我更倾向于用 RAII 管理资源，优先使用 std::unique_ptr、std::shared_ptr、std::weak_ptr、std::vector、std::string 等标准库对象，减少裸 new/delete，让资源生命周期和对象生命周期绑定。

## 7. 面试追问

### 7.1 内存泄漏和内存碎片有什么区别？

内存泄漏是内存已经无法释放，因为程序失去了释放它的机会或指针。

内存碎片是内存仍然被分配器管理，但是由于频繁申请和释放，空闲内存不连续，导致内存利用率下降。

---

### 7.2 shared_ptr 一定不会内存泄漏吗？

不是。

`shared_ptr` 可以自动管理引用计数，但如果两个对象互相持有 `shared_ptr`，就会产生循环引用，引用计数无法归零，导致对象无法析构。

解决方式是把其中一边改成 `weak_ptr`。

---

### 7.3 为什么推荐 RAII？

RAII 的核心是把资源释放放到析构函数中。

对象离开作用域时会自动析构，所以即使遇到异常、提前 return，也能自动释放资源。

典型例子：

```cpp
std::unique_ptr<T>
std::shared_ptr<T>
std::vector<T>
std::string
std::lock_guard<std::mutex>
std::fstream
```

---

### 7.4 delete 和 delete[] 用错会怎样？

`new` 要配 `delete`，`new[]` 要配 `delete[]`。

如果 `new[]` 后使用 `delete`，可能导致数组元素析构不完整，行为未定义。

---

### 7.5 如何判断内存上涨是缓存还是泄漏？

可以看内存是否有上限和回收机制：

1. 缓存通常有容量限制、淘汰策略，达到稳定状态后内存会趋于平稳
2. 泄漏通常没有稳定上限，随着请求或时间持续增长
3. 可以通过压测观察相同流量下内存是否最终收敛
4. 可以用 heaptrack 或 pprof 看增长对象是否来自业务缓存还是异常分配路径

---

## 8. 最佳实践

1. 少用裸 `new/delete`
2. 优先使用 RAII
3. 独占所有权用 `std::unique_ptr`
4. 共享所有权用 `std::shared_ptr`
5. 打破循环引用用 `std::weak_ptr`
6. 数组和缓冲区优先用 `std::vector`、`std::array`、`std::string`
7. 锁资源用 `std::lock_guard` 或 `std::unique_lock`
8. 文件、socket、fd 等资源也要封装成对象管理
9. 缓存必须有容量上限或淘汰策略
10. 在 CI 或测试环境中开启 ASan/LSan

---

## 9. 一句话总结

C++ 内存泄漏排查的核心不是简单地找 `delete`，而是确认内存增长来源，定位分配栈，理清资源所有权，并用 RAII 和智能指针把资源生命周期管理起来。
