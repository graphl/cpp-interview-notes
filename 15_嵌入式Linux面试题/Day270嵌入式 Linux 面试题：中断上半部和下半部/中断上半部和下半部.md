# 嵌入式 Linux 面试题：中断上半部和下半部

## 1. 面试主要考什么？

中断处理考的是：硬件事件来了以后，内核如何快速响应，又如何把耗时工作延后处理。

面试官想听到：

1. 硬中断上下文
2. 上半部要快
3. 下半部处理耗时任务
4. tasklet、workqueue、threaded irq
5. 中断上下文不能睡眠
6. 共享中断和中断风暴

---

## 2. 控制流

```text
硬件产生 IRQ
  -> GIC/中断控制器
  -> CPU 进入异常向量
  -> 内核通用中断框架
  -> 驱动注册的 irq_handler
  -> 清中断状态
  -> 唤醒下半部
```

下半部：

```text
irq_handler()
  -> schedule_work()
  -> kworker 线程
  -> workqueue 回调
  -> 可以睡眠、可以执行较慢逻辑
```

---

## 3. 上半部做什么？

上半部通常只做：

1. 判断是不是自己的中断
2. 读取状态寄存器
3. 清除中断状态
4. 保存必要数据
5. 唤醒等待队列或调度下半部

不要做：

1. 长时间循环
2. 大量拷贝
3. 睡眠
4. 可能阻塞的 IO
5. 复杂业务逻辑

---

## 4. 下半部方案对比

| 机制 | 是否能睡眠 | 适合场景 |
|---|---|---|
| softirq | 不能 | 网络、块设备等高频路径 |
| tasklet | 不能 | 较老的轻量延后处理 |
| workqueue | 能 | 需要睡眠或较耗时的任务 |
| threaded irq | 能 | 驱动中常用，逻辑清晰 |

---

## 5. threaded irq 示例

```cpp
static irqreturn_t demo_irq_top(int irq, void* dev_id) {
    return IRQ_WAKE_THREAD;
}

static irqreturn_t demo_irq_thread(int irq, void* dev_id) {
    // 可以做相对耗时的处理
    return IRQ_HANDLED;
}

ret = request_threaded_irq(irq, demo_irq_top, demo_irq_thread,
                           IRQF_TRIGGER_RISING, "demo", data);
```

---

## 6. 调试方法

命令：

```text
cat /proc/interrupts
dmesg | grep -i irq
cat /proc/irq/<irq>/smp_affinity
echo 1 > /proc/sys/kernel/printk
```

观察：

1. 中断计数是否增长
2. 是否绑定到预期 CPU
3. 是否出现中断风暴
4. handler 是否返回 `IRQ_HANDLED`

---

## 7. 常见坑

1. 上半部里睡眠
2. 忘记清中断，导致中断风暴
3. 共享中断没判断设备状态
4. 中断触发方式配置错
5. GPIO pinctrl 没配置
6. 没释放 IRQ

---

## 8. 面试回答

中断上半部运行在硬中断上下文，要求尽快返回，一般只做状态读取、清中断、保存少量数据和唤醒下半部。耗时工作放到下半部，比如 workqueue 或 threaded irq。中断上下文不能睡眠，所以不能调用可能阻塞的接口。调试时我会看 `/proc/interrupts` 的计数是否增长，检查设备树里的中断号和触发方式，并确认中断处理函数里是否正确清除了硬件中断状态。
