# C++ 面试题：USE 方法如何建立性能排查闭环

## 1. 这个方法解决什么问题

性能排查最常见的错误是先运行熟悉的工具，再从海量指标里猜原因。USE 方法先按资源检查：

```text
Utilization：资源有多长时间忙碌，或容量用了多少
Saturation ：需求超过服务能力后，有多少任务在排队
Errors     ：资源或操作是否发生错误
```

它适合快速建立系统级排查范围，但最终仍需通过调用栈、时间线或实验验证根因。

## 2. 从症状到证据的数据流

```text
业务症状：延迟升高/吞吐下降/抖动
  -> 明确时间窗口、受影响请求和基线
  -> 列出 CPU、内存、磁盘、网络等资源
  -> 对每类资源检查 U/S/E
  -> 找到异常资源与异常时间段
  -> 下钻到进程、线程、调用栈、锁或 IO 请求
  -> 提出单一可证伪假设
  -> 用实验或更细证据验证
  -> 修复后复测业务指标和副作用
```

## 3. 常用资源检查表

| 资源 | Utilization | Saturation | Errors/异常 | 常用入口 |
|---|---|---|---|---|
| CPU | `%usr/%sys`、每核利用率 | run queue、调度延迟 | soft lockup、节流 | `mpstat`、`pidstat`、`perf` |
| 内存 | RSS、cache、NUMA 使用 | reclaim、swap、分配停顿 | OOM、分配失败 | `free`、`vmstat`、`numastat` |
| 磁盘 | `%util`、吞吐 | await、队列深度 | IO error、reset | `iostat -xz`、`dmesg` |
| 网络 | 带宽、包速率 | backlog、socket 队列 | drop、retransmit | `sar -n DEV`、`ss -ti`、`ethtool -S` |
| 锁 | 持锁时间 | 等锁线程、futex 等待 | 死锁/超时 | `perf lock`、off-CPU 分析 |

`%util=100%` 的含义与设备并行能力有关，不能单独等价为“磁盘已经达到最大吞吐”。指标必须结合延迟、队列和硬件模型解释。

## 4. 示例：接口延迟突然升高

```text
1. 确认只有某台机器受影响，时间为 10:02-10:08。
2. vmstat 发现 run queue 明显升高，但 CPU idle 仍存在。
3. pidstat -w 发现目标线程自愿上下文切换暴增。
4. perf/futex 或 off-CPU 栈显示大量线程等待同一把锁。
5. 假设：新版本把慢 IO 放进全局锁临界区。
6. 对照代码和 trace 验证持锁区间确实覆盖 IO。
7. 缩小临界区后，用相同负载复测 P99、吞吐和错误率。
```

这说明“CPU 看起来不满”不代表 CPU 路径没有问题，线程可能在锁或 IO 上睡眠。

## 5. 最小命令集

```bash
uptime
vmstat 1
mpstat -P ALL 1
pidstat -p $PID -t -u -w 1
iostat -xz 1
sar -n DEV,TCP,ETCP 1
ss -s
perf top -p $PID
```

先保存原始输出和时间戳，再做重启、限流或参数修改，否则现场证据可能丢失。

## 6. 面试口述版

我会先把业务症状限定到时间、实例和请求类型，再按 CPU、内存、磁盘、网络等资源检查利用率、饱和度和错误。发现异常资源后下钻到进程、线程和调用栈，提出可证伪假设，用 trace 或对照实验验证，最后用相同负载复测业务指标。工具只是取证手段，完整结果必须形成症状、证据、假设、验证和复测闭环。
