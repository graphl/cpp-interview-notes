# C++ 面试题：原子操作和多线程

## 1. 面试主要考什么？

这道题主要考你是否理解：

1. 为什么多线程需要原子操作
2. `atomic` 和普通变量的区别
3. `atomic` 和 `mutex` 的区别
4. CAS 是什么
5. 内存序是什么
6. `atomic` 不能解决哪些问题
7. 原子操作和对象生命周期的关系

核心一句话：

> 原子操作用于保证简单共享变量在多线程访问时没有 data race，并通过内存序控制线程之间的可见性和顺序关系。

---

## 2. 为什么需要原子操作？

普通变量的自增不是一步完成的。

```cpp
int count = 0;

++count;
```

底层大致可以拆成：

```text
读取 count
  -> 加 1
  -> 写回 count
```

多个线程同时执行时，可能发生丢失更新。

```cpp
std::atomic<int> count{0};

++count;
```

`std::atomic` 可以保证这个读改写操作整体是原子的，不会出现普通变量并发读写导致的 data race。

---

## 3. atomic 和 mutex 有什么区别？

| 对比 | atomic | mutex |
|---|---|---|
| 保护范围 | 单个变量或简单状态 | 一段临界区 |
| 是否可能阻塞 | 通常不阻塞 | 可能阻塞 |
| 适合场景 | 计数器、状态标志、引用计数 | 容器、多变量、复杂对象 |
| 使用难度 | 内存序难，容易写错 | 逻辑更直观 |
| 能否保护对象生命周期 | 不能单独保证 | 可以作为生命周期同步的一部分 |

核心区别：

```text
atomic 保护的是一次变量访问或一次原子更新；
mutex 保护的是一段代码和一组共享状态。
```

例如：

```cpp
if (!q.empty()) {
    auto x = q.front();
    q.pop();
}
```

这个逻辑需要保证 `empty`、`front`、`pop` 整体一致，不能靠一个 `atomic` 解决，应该用 `mutex` 保护队列。

---

## 4. atomic 常见操作有哪些？

```cpp
#include <atomic>

std::atomic<int> count{0};
std::atomic<bool> stop{false};

count.fetch_add(1);
count.fetch_sub(1);

int old = count.load();
count.store(10);

bool expected = false;
bool ok = stop.compare_exchange_strong(expected, true);
```

常见接口：

1. `load()`：原子读取
2. `store()`：原子写入
3. `fetch_add()`：原子加
4. `fetch_sub()`：原子减
5. `exchange()`：原子交换
6. `compare_exchange_strong()`：强 CAS
7. `compare_exchange_weak()`：弱 CAS，可能虚假失败

---

## 5. CAS 是什么？

CAS 是 Compare And Swap。

逻辑是：

```text
如果当前值 == 期望值：
    把当前值改成新值
否则：
    把当前值写回 expected，并返回失败
```

示例：

```cpp
std::atomic<int> value{0};

int expected = 0;
bool ok = value.compare_exchange_strong(expected, 1);
```

如果 `value` 当前是 0，就改成 1，并返回 true。
如果 `value` 当前不是 0，CAS 失败，并把当前值写回 `expected`。

## 6. 内存序是什么？

原子操作不只保证变量读写不可分割，还涉及：

```text
一个线程写入的数据，
另一个线程什么时候能看到。
```

常见内存序：

| 内存序 | 含义 |
|---|---|
| `memory_order_relaxed` | 只保证原子性，不保证同步顺序 |
| `memory_order_acquire` | 获取语义，后面的读写不能跑到它前面 |
| `memory_order_release` | 释放语义，前面的读写不能跑到它后面 |
| `memory_order_acq_rel` | acquire + release |
| `memory_order_seq_cst` | 最强顺序，默认内存序 |

面试里最常见的是：

```text
release 用来发布数据；
acquire 用来获取数据。
```

---

## 7. release-acquire 怎么理解？

```cpp
#include <atomic>
#include <string>

std::string data;
std::atomic<bool> ready{false};

void producer() {
    data = "hello";
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
    }

    use(data);
}
```

含义：

```text
producer:
写 data
  -> release 写 ready

consumer:
acquire 读 ready
  -> 读 data
```

当 consumer 看到 `ready == true` 后，也能看到 producer 在 release 之前写入的 `data`。

---

## 8. relaxed 什么时候能用？

`memory_order_relaxed` 只保证这个变量本身的读写是原子的，不保证它和其他变量之间的同步关系。

适合：

1. 统计计数
2. 性能指标
3. 不影响程序正确性的累计值

示例：

```cpp
std::atomic<long> request_count{0};

void on_request() {
    request_count.fetch_add(1, std::memory_order_relaxed);
}
```

如果只是统计请求数，不用通过这个计数通知另一个线程读取其他数据，用 relaxed 可以。

---

## 9. atomic 能替代锁吗？

不能完全替代。

这些场景通常更适合用锁：

1. 修改 STL 容器
2. 多个变量之间有一致性要求
3. 一段复杂逻辑要整体执行
4. 需要等待某个条件成立
5. 需要保护对象生命周期
6. 析构和回调可能并发

例子：

```cpp
struct Account {
    int balance;
    int version;
};
```

如果 `balance` 和 `version` 必须一起更新，只把它们改成 `atomic<int>` 不一定能保证对象整体一致。
这种情况更适合用 `mutex` 保护整个对象。

---

## 10. atomic 能解决对象生命周期问题吗？

不能。

错误示例：

```cpp
std::atomic<bool> running{true};
Worker* worker = new Worker;

std::thread t([&] {
    while (running.load()) {
        worker->do_work();
    }
});

delete worker;
running.store(false);
t.join();
```

虽然 `running` 是原子的，但 `worker` 可能已经被释放，线程还在访问它。
这仍然会产生 use-after-free。

正确思路：

```text
先通知线程退出
  -> 唤醒线程
  -> join 等待线程结束
  -> 再释放对象
```

原子变量只能作为退出通知的一部分，不能替代完整的生命周期设计。

---

## 11. ABA 问题是什么？

CAS 只比较当前值是否等于期望值。

ABA 问题是：

```text
线程 1 看到值是 A
线程 2 把 A 改成 B
线程 2 又把 B 改回 A
线程 1 再 CAS，发现还是 A，以为没变过
```

但实际上中间已经发生过变化。

常见解决思路：

1. 给指针加版本号
2. 使用 tagged pointer
3. 使用 hazard pointer
4. 使用 epoch-based reclamation
5. 直接用锁简化设计

## 12. 高频追问

### 12.1 atomic 一定比 mutex 快吗？

不一定。

原因：

1. 高竞争下 atomic 也会造成 cache line 抖动
2. CAS 失败会不断重试
3. 无锁代码更难写对
4. 复杂临界区用 mutex 更清晰

### 12.2 volatile 能替代 atomic 吗？

不能。

`volatile` 主要告诉编译器不要优化掉这次访问。
它不保证原子性，也不建立线程间同步关系。

多线程同步应该用 `atomic`、`mutex`、条件变量等工具。

### 12.3 shared_ptr 的引用计数是不是原子的？

通常控制块里的引用计数操作是线程安全的。

但是：

```text
多个 shared_ptr 实例共享同一个控制块，引用计数安全；
多个线程同时读写同一个 shared_ptr 变量本身，不一定安全；
shared_ptr 管理的对象内部状态，也不自动线程安全。
```

### 12.4 memory_order_seq_cst 是什么？

`seq_cst` 是默认内存序，也是最强内存序。
它提供全局一致的顺序，最容易理解，但可能不是性能最优。

面试中如果不确定，先说默认使用 `seq_cst` 更安全，再补充高性能场景才会谨慎使用更弱内存序。

---

## 13. 常见错误回答

1. 说 `atomic` 一定比锁快
2. 说 `volatile` 可以保证线程安全
3. 认为用了 `atomic<bool>` 就不会有生命周期问题
4. 用 atomic 强行保护 STL 容器
5. 只知道 CAS，不知道 ABA
6. 乱用 `memory_order_relaxed` 做线程通知
7. 忽略对象内部状态仍然需要同步

---

## 14. 面试回答模板

可以这样回答：

> 原子操作主要用于多线程下对简单共享变量进行安全读写，比如计数器、状态标志、引用计数和 stop flag。普通变量的读改写不是一步完成的，多线程并发访问会产生 data race，而 `std::atomic` 可以保证单次读写或读改写是原子的。它和 `mutex` 的区别是，`atomic` 适合保护单个变量或简单状态，`mutex` 适合保护一段临界区、容器或多个变量之间的不变量。使用 atomic 时还要考虑内存序，默认是 `seq_cst`，如果用 release-acquire，可以建立线程间的可见性关系。需要注意的是，atomic 不能自动解决对象生命周期问题，也不能完全替代锁，复杂共享状态通常还是应该用 mutex。

---

## 15. 最终背诵版

原子操作的本质是：

```text
保证简单共享变量的原子访问，
并通过内存序控制多线程之间的数据可见性和执行顺序。
```

面试中一定要补一句：

```text
atomic 不是万能的。
它不能自动保护复杂对象、STL 容器、多变量一致性和对象生命周期。
```
