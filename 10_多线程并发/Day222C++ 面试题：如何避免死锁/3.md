## 实际场景 4：读写锁升级死锁

读写锁允许多个读者同时持有读锁，但写锁需要独占。

危险场景：

```text
线程 A 持有读锁，想升级成写锁
线程 B 持有读锁，也想升级成写锁
```

两者都不释放读锁，又都等写锁，就可能卡死。

避免方式：

1. 不要在持有读锁时直接升级写锁
2. 先释放读锁，再重新申请写锁
3. 重新申请写锁后要再次检查条件

---

## 什么锁容易死锁？

| 锁/机制                | 是否容易死锁                   | 原因                                         |
| ---------------------- | ------------------------------ | -------------------------------------------- |
| `std::mutex`           | 容易                           | 最常用的互斥锁，多把锁顺序不一致就容易死锁   |
| `std::recursive_mutex` | 容易隐藏问题                   | 允许同一线程重复加锁，可能掩盖设计问题       |
| `std::timed_mutex`     | 相对可控                       | 可以超时返回，但逻辑处理不好仍然会死锁或活锁 |
| `std::shared_mutex`    | 容易                           | 读写锁在锁升级、写者饥饿场景容易出问题       |
| 自旋锁                 | 容易造成卡死/CPU 打满          | 持锁线程不运行时，等待线程会一直忙等         |
| 条件变量               | 本身不是锁，但容易写出等待死锁 | 条件、锁、通知顺序写错会导致线程永远睡眠     |
| 信号量                 | 可能死锁                       | acquire/release 不平衡或资源顺序反了会卡住   |
| 文件锁/进程锁          | 可能死锁                       | 多进程持有不同资源互等                       |

---

## 什么机制不容易死锁？

严格说，只要存在“等待别人释放资源”，就有可能设计出死锁。但下面这些机制相对不容易形成传统死锁：

| 机制                | 为什么不容易死锁               | 注意点                       |
| ------------------- | ------------------------------ | ---------------------------- |
| `std::atomic`       | 不需要互斥锁，不会持锁等待     | 可能有 ABA、内存序、忙等问题 |
| 无锁队列            | 避免 mutex 阻塞等待            | 实现复杂，可能有活锁         |
| 消息队列/Actor 模型 | 通过消息串行化状态，减少共享锁 | 队列阻塞、背压处理不好也会卡 |
| 单线程事件循环      | 状态在一个线程内串行处理       | 不能在事件循环里做阻塞操作   |
| RAII 锁管理         | 自动释放锁，减少忘记 unlock    | 不能解决多锁顺序问题         |
| `std::scoped_lock`  | 多把锁一起加，避免常见交叉死锁 | 只解决同一处同时加多锁的问题 |

重点：

```text
atomic 不会产生 mutex 那种互相持锁等待的死锁，
但不代表 atomic 写出来的并发代码一定正确。
```
