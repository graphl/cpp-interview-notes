# 原子操作和多线程总结

## 1. 原子操作解决什么问题

多线程里，多个线程同时访问同一个变量，如果至少有一个线程在写，并且没有同步，就会产生 data race。

原子操作解决的是：

```text
多个线程同时读写同一个简单变量时，
保证这个变量的读、写、修改不会被其他线程打断。
```

典型场景：

1. 计数器
2. 状态标志
3. 引用计数
4. stop flag
5. CAS 更新状态
6. 无锁队列、无锁栈里的指针更新

---

## 2. atomic 和普通变量的区别

普通变量：

```cpp
int count = 0;

// 多线程同时执行
++count;
```

`++count` 不是一步操作，通常会拆成：

```text
读取 count
  -> 加 1
  -> 写回 count
```

多个线程同时执行时，可能发生丢失更新。

原子变量：

```cpp
std::atomic<int> count{0};

// 多线程同时执行
++count;
```

`std::atomic` 保证这个读改写操作整体是原子的，不会发生普通变量那种 data race。

---

## 3. atomic 和 mutex 的区别

| 对比 | atomic | mutex |
|---|---|---|
| 保护对象 | 单个变量或简单状态 | 一段临界区 |
| 是否阻塞 | 通常不阻塞 | 可能阻塞 |
| 适合场景 | 计数、标志、简单状态机 | 复杂对象、容器、多变量不变量 |
| 使用难度 | 内存序难 | 逻辑更直观 |
| 能否保护 STL 容器 | 不适合 | 适合 |

核心区别：

```text
atomic 保护的是一次变量访问或一次原子更新；
mutex 保护的是一段代码和这段代码里的共享状态。
```

如果多个变量之间有关系，通常应该用锁。

例如：

```cpp
if (!q.empty()) {
    auto x = q.front();
    q.pop();
}
```

这里不是一个变量的原子更新，而是一组操作必须整体成立，所以应该用 `mutex`。

---

## 4. atomic 常见操作

```cpp
#include <atomic>

std::atomic<int> count{0};
std::atomic<bool> stop{false};

count.fetch_add(1);
count.fetch_sub(1);

int old = count.load();
count.store(10);

bool expected = false;
bool ok = stop.compare_exchange_strong(expected, true);
```

常见接口：

1. `load()`：原子读取
2. `store()`：原子写入
3. `fetch_add()`：原子加
4. `fetch_sub()`：原子减
5. `exchange()`：原子交换
6. `compare_exchange_strong()`：CAS
7. `compare_exchange_weak()`：弱 CAS，可能虚假失败

---

## 5. CAS 是什么

CAS 是 Compare And Swap。

逻辑是：

```text
如果当前值 == 期望值：
    把当前值改成新值
否则：
    更新期望值为当前值，并返回失败
```

示例：

```cpp
std::atomic<int> value{0};

int expected = 0;
bool ok = value.compare_exchange_strong(expected, 1);
```

如果 `value` 当前是 0，就改成 1，并返回 true。
如果 `value` 当前不是 0，就把当前值写回 `expected`，并返回 false。

CAS 常用于无锁结构，但会带来 ABA 问题。

## 6. 内存序是什么

原子操作不只解决“操作不可分割”，还涉及“其他线程什么时候能看到前后的内存操作”。

这就是内存序。

常见内存序：

| 内存序 | 含义 |
|---|---|
| `memory_order_relaxed` | 只保证原子性，不保证同步顺序 |
| `memory_order_acquire` | 读屏障，后面的读写不能跑到它前面 |
| `memory_order_release` | 写屏障，前面的读写不能跑到它后面 |
| `memory_order_acq_rel` | acquire + release |
| `memory_order_seq_cst` | 最强顺序，默认内存序 |

面试中最常见的是：

```text
release 写发布数据；
acquire 读获取数据。
```

---

## 7. release-acquire 示例

```cpp
#include <atomic>
#include <string>

std::string data;
std::atomic<bool> ready{false};

void producer() {
    data = "hello";
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
    }

    // 看到 ready == true 后，也能看到 producer 写入的 data
    use(data);
}
```

含义：

```text
producer:
data = "hello"
  -> release store ready = true

consumer:
acquire load ready == true
  -> 之后读取 data
```

`release` 和 `acquire` 配对后，可以建立 happens-before 关系。

---

## 8. relaxed 适合什么场景

`memory_order_relaxed` 只保证这个变量本身的读写是原子的，不保证和其他变量之间的可见顺序。

适合：

1. 统计计数
2. 性能指标
3. 不影响程序正确性的累计值

示例：

```cpp
std::atomic<long> request_count{0};

void on_request() {
    request_count.fetch_add(1, std::memory_order_relaxed);
}
```

如果只是统计请求数量，不需要通过这个计数同步其他数据，用 relaxed 可以。

不适合：

```text
用一个 flag 通知另一个线程读取普通数据。
```

这种需要 release-acquire 或锁。

---

## 9. atomic 不能替代锁的场景

这些场景通常不要硬用 atomic：

1. 修改 STL 容器
2. 多个变量必须保持一致
3. 需要执行一段复杂逻辑
4. 需要等待条件成立
5. 需要保护对象生命周期
6. 需要避免回调和析构并发

例子：

```cpp
struct Account {
    int balance;
    int version;
};
```

如果 `balance` 和 `version` 必须一起更新，单独把它们改成 `atomic<int>` 不一定能保证整体一致性。
这种情况更适合用 `mutex` 保护整个对象。

---

## 10. atomic 和对象生命周期

原子操作能保证变量读写安全，但不能自动保证对象还活着。

危险例子：

```cpp
std::atomic<bool> running{true};
Worker* worker = new Worker;

std::thread t([&] {
    while (running.load()) {
        worker->do_work();
    }
});

delete worker;
running.store(false);
t.join();
```

这里即使用了 `atomic<bool>`，仍然可能发生 use-after-free。

正确方向：

```text
先通知线程退出
  -> 唤醒线程
  -> join 等待线程结束
  -> 再释放对象
```

atomic 只能做同步的一部分，不能替代完整生命周期设计。

---

## 11. ABA 问题

CAS 只比较“当前值是否等于期望值”。

ABA 问题是：

```text
线程 1 看到值是 A
线程 2 把 A 改成 B
线程 2 又把 B 改回 A
线程 1 再 CAS，发现还是 A，以为没变过
```

但实际上中间已经发生过变化。

常见解决思路：

1. 给指针加版本号
2. 使用 tagged pointer
3. 使用 hazard pointer
4. 使用 epoch-based reclamation
5. 简化设计，直接用锁

面试里要说明：无锁不是只会 CAS，还要处理内存回收和 ABA。

## 12. 面试高频问题

### 12.1 atomic 一定比 mutex 快吗？

不一定。

原因：

1. atomic 在高竞争下也会导致 cache line 抖动
2. CAS 失败会重试
3. 无锁代码更难写对
4. 复杂临界区用 mutex 更清晰

### 12.2 volatile 能替代 atomic 吗？

不能。

`volatile` 主要告诉编译器不要优化掉这次访问，不保证原子性，也不建立线程间同步关系。

多线程同步应该用 `atomic`、`mutex`、条件变量等工具。

### 12.3 shared_ptr 的引用计数是不是原子的？

通常控制块里的引用计数操作是线程安全的。

但注意：

```text
多个 shared_ptr 实例共享同一对象，引用计数安全；
多个线程同时读写同一个 shared_ptr 变量本身，不一定安全。
```

也就是说，对象生命周期可以被引用计数保护，但对象内部状态仍然需要同步。

### 12.4 atomic 能保护对象内部状态吗？

不能自动保护。

如果对象内部有多个字段，或者字段之间有不变量，需要锁或更明确的同步设计。

---

## 13. 面试回答模板

回答原子操作时，可以按这个顺序：

```text
先说它解决什么问题
  -> 再说和 mutex 的区别
  -> 再说常见操作
  -> 再补充内存序
  -> 最后说不能滥用和常见坑
```

示例回答：

> 原子操作主要用于多线程下对简单共享变量进行无 data race 的读写，比如计数器、状态标志、引用计数。它保证单次读写或读改写是不可分割的。和 `mutex` 不同，`atomic` 更适合保护单个变量或简单状态，而 `mutex` 适合保护一段临界区、容器或多个变量之间的不变量。使用 `atomic` 时还要考虑内存序，默认是最强的 `seq_cst`，如果用 `release/acquire`，可以建立线程间的可见性关系。需要注意的是，`atomic` 不能自动解决对象生命周期问题，也不能随便替代锁，复杂共享状态通常还是应该用 `mutex`。

---

## 14. 总结

原子操作在多线程中的本质是：

```text
保证简单共享变量的原子访问，
并通过内存序控制线程之间的可见性和顺序关系。
```

但多线程程序正确性不只靠原子操作，还要同时考虑：

```text
共享资源
  -> 同步方式
  -> 内存序
  -> 对象生命周期
  -> 退出流程
  -> 调试排查
```
