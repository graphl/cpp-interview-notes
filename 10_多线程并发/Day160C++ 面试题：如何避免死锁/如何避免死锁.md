# C++ 面试题：如何避免死锁？

## 1. 核心结论

避免死锁不能只背“四个必要条件”，要能说出实际场景。

死锁本质是：

```text
线程 A 持有资源 1，等待资源 2
线程 B 持有资源 2，等待资源 1
```

工程上最常见的避免方式：

1. 固定多把锁的加锁顺序
2. 多把锁使用 `std::lock` 或 `std::scoped_lock`
3. 不要持锁调用外部代码、回调、日志、网络 IO
4. 不要持锁 `join` 线程
5. 缩小临界区
6. 必要时使用 `try_lock` 或超时锁

## 2. 实际死锁场景

### 2.1 转账场景

```text
线程 A：锁 account1，再锁 account2
线程 B：锁 account2，再锁 account1
```

两个线程互相等待。

解决：

```cpp
std::scoped_lock lock(account1.mtx, account2.mtx);
```

---

### 2.2 业务锁和日志锁

```text
业务线程：business_mutex -> log_mutex
日志线程：log_mutex -> business_mutex
```

解决：

```text
持锁时不要调用日志模块或外部回调
先复制数据，释放锁后再调用外部函数
```

---

### 2.3 持锁 join

```text
主线程拿着 mutex 等 worker.join()
worker 退出前也要拿 mutex
```

解决：

```text
先释放锁，再 join
```

## 3. 哪些锁容易死锁？

| 锁/机制 | 风险 |
|---|---|
| `std::mutex` | 多把锁顺序不一致最容易死锁 |
| `std::recursive_mutex` | 容易掩盖设计问题 |
| `std::shared_mutex` | 读写锁升级容易死锁 |
| 自旋锁 | 持锁线程不运行时，其他线程会一直忙等 |
| 条件变量 | 条件和通知写错会导致永久等待 |
| 信号量 | acquire/release 不平衡会卡住 |

---

## 4. 哪些机制不容易形成传统死锁？

| 机制 | 说明 |
|---|---|
| `std::atomic` | 不持有互斥锁，不会形成 mutex 互等死锁 |
| 消息队列 | 通过消息传递减少共享锁 |
| 单线程事件循环 | 状态串行处理，不需要多线程锁 |
| `std::scoped_lock` | 多把锁一起加，降低交叉死锁风险 |

注意：

```text
atomic 不容易产生传统死锁，但可能有 ABA、内存序错误、活锁或忙等问题。
```

---

## 5. 面试背诵版

死锁的本质是多个线程互相等待对方持有的资源。实际开发里常见场景包括多把锁顺序不一致、业务锁和日志锁互相嵌套、持锁调用回调、持锁 join 线程、读写锁升级。避免死锁主要靠统一加锁顺序，多把锁用 `std::lock` 或 `std::scoped_lock`，减少锁持有时间，不在持锁时调用外部代码或阻塞操作。`mutex`、读写锁、自旋锁、信号量都可能死锁；`atomic` 不会形成传统互斥锁死锁，但仍然可能有活锁或内存序问题。
