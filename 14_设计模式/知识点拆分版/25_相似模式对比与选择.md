# 设计模式：相似模式如何对比与选择

## 1. 先找变化轴，不要先背模式名

设计模式解决的是反复出现的变化与依赖问题。面对场景题先问：

```text
谁在变化？
  ├── 对象创建过程        -> 创建型模式
  ├── 对象之间的组合结构  -> 结构型模式
  └── 行为、状态或协作流程 -> 行为型模式
```

如果没有明确变化点，强行套模式只会增加间接层和生命周期成本。

## 2. 创建型模式怎么选

| 模式 | 变化点 | 典型信号 |
|---|---|---|
| 简单工厂 | 根据参数选择具体类型 | 类型少、创建逻辑集中 |
| 工厂方法 | 由子类/具体工厂决定产品 | 新增产品时希望扩展而非修改判断 |
| 抽象工厂 | 创建一整族相互匹配的产品 | UI 主题、跨平台组件族 |
| 建造者 | 同一复杂对象有不同构建步骤/配置 | 参数多、构建过程分阶段 |
| 原型 | 复制已有对象比重新构造更自然 | 动态配置对象、克隆成本可控 |

```text
只选择一个具体类？       -> 简单工厂/工厂方法
要保证一组产品彼此兼容？ -> 抽象工厂
产品类型固定但装配步骤多？ -> 建造者
从现有实例复制？          -> 原型
```

## 3. Adapter、Decorator、Proxy、Facade

它们都可能“包一层对象”，但目的不同：

| 模式 | 核心目的 | 接口是否通常相同 | 例子 |
|---|---|---|---|
| Adapter | 转换不兼容接口 | 不同 | 把旧库接口适配成新接口 |
| Decorator | 动态叠加职责 | 相同 | 流的压缩、加密、缓冲 |
| Proxy | 控制访问 | 相同 | 延迟加载、权限、远程代理 |
| Facade | 为复杂子系统提供简单入口 | 新的高层接口 | 编译子系统的一键调用 |

判断句：

```text
调用方不会用旧接口       -> Adapter
调用前后要附加可组合功能 -> Decorator
要决定是否/何时/在哪里调用真实对象 -> Proxy
子系统接口太多，需要统一入口 -> Facade
```

## 4. Strategy、State、Template Method

| 模式 | 谁决定变化 | 结构重点 |
|---|---|---|
| Strategy | 调用者/配置选择算法 | 多个可替换算法实现统一接口 |
| State | 对象内部状态推动行为切换 | 状态对象和状态迁移 |
| Template Method | 基类固定流程骨架，子类改步骤 | 继承和受保护扩展点 |

Strategy 和 State 类图可能相似，但语义不同：策略通常由外部选择，状态模式的切换通常是业务状态机的一部分。Template Method 使用继承；Strategy 使用组合，运行时替换通常更自然。

## 5. Observer、Mediator、Event Bus

```text
Observer：一个主题向多个观察者发布变化
Mediator：多个同事对象通过中心协调者交互
Event Bus：以消息主题进一步解耦发布者和订阅者
```

C++ 实现必须先设计订阅生命周期：

1. 谁拥有观察者？
2. 对象销毁时如何取消订阅？
3. 回调执行期间能否增删订阅者？
4. 是否跨线程，回调在哪个线程执行？
5. 捕获裸 `this` 是否可能悬空？

## 6. Bridge 和 Strategy 为什么容易混

Strategy 通常替换一个行为算法；Bridge 同时抽象两个可独立变化的维度：

```text
遥控器抽象层 <----组合----> 设备实现层
     独立扩展                   独立扩展
```

如果只是“排序算法可替换”，优先想到 Strategy；如果“业务抽象层”和“平台实现层”都要形成独立继承层次，才更像 Bridge。

## 7. C++ 工程边界

- 用 `unique_ptr` 表达装饰器、状态或策略的独占所有权。
- 共享并不自动意味着 `shared_ptr`；先明确真实所有者。
- Observer 和异步 Command 最容易出现悬空回调与循环引用。
- Singleton 带来全局状态、初始化顺序和测试隔离问题，应先考虑依赖注入。
- 模式增加抽象层，必须换来可验证的变化隔离，而不是为了类图好看。

## 8. 面试回答模板

```text
1. 当前变化点是……
2. 如果直接用条件分支/继承，会导致……
3. 选择某模式后，稳定部分是……，可替换部分是……
4. 对象所有权和生命周期由……负责
5. 相比相似模式，不选择它们是因为……
6. 如果变化规模很小，我会先用更简单实现，达到边界后再重构
```
